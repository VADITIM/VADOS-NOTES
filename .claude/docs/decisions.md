# Decisions

Reasons that would otherwise be comments. The spec's section 11 is the product-level log; this file is the code-level one.

## Core (`ios/NotesCore`)

- **Journal replay merges, it does not overwrite.** State is the synced snapshot plus every journal entry applied through the merge rules, so a newer remote edit still beats an older local one after a pull.
- **Snapshot is the last remote state, not the last local one.** A pull replaces snapshot files with remote bytes; local work lives only in the journal until a push lands.
- **Entries are removed by sequence, not "through" a sequence.** Entries for blocked pages (corrupt or newer schema on the remote) stay in the journal while the rest are removed.
- **A push only includes entries that existed when the files were built.** Building the files and capturing the sequences happen without a suspension point, so changes made during the network calls stay in the journal for the next flush.
- **409 and 422 both mean "branch moved".** GitHub answers a non-fast-forward ref update with 422; the spec's wording said 409.
- **An empty repository is started through the contents API.** The Git Data API refuses blobs on a repository with no commits, so the first commit is a README written with `PUT contents`.
- **Extent merges as the union of both axes.** Extent only ever grows, so taking the larger value per axis needs no timestamp and cannot lose an expansion.
- **Equal timestamps break ties by device name.** Keeps the element merge commutative.
- **Timestamps are rounded to milliseconds when created.** They round-trip through the file format exactly, so a decoded page equals the page that was written.
- **Points are rounded to 0.01 mm and thinned below 0.15 mm.** Same bytes on every platform, and Pencil's 240 Hz samples do not bloat the files.
- **Tool opacity is not stored per stroke.** It comes from `shared/tokens.json` by tool, so marker translucency is one definition for both renderers.

## iPad app (`ios/VadosNotes`)

- **Custom canvas, no PencilKit.** Points are the stored truth and are drawn as constant-width paths; nothing to strip out of PencilKit's pressure model.
- **Once a Pencil touch is seen, one finger pans instead of drawing.** Palm rejection without a setting. Before any Pencil touch, a finger draws.
- **A finger held still for 450 ms opens the page menu**, and the stroke it started is discarded. The Pencil never opens menus.
- **The menu opens above the finger**, so lifting without moving selects nothing; sliding onto a slot and lifting selects it.
- **Destructive slots arm on the first tap and act on the second** (V/AS confirm pattern, inside the menu).
- **Undo of an erase re-creates the stroke under a new ID.** A tombstone always wins a merge, so reviving the old ID would be undone by the next sync.
- **A new text block is journaled only once it has a character.** Abandoned empty blocks never reach the repo.
- **No blur, no glass, no shadows.** The spec overrides the Gallery's glass pill: the pop bar is a flat `panel_solid` capsule with a hairline.
- **One accent (`#FFDD1B`) app-wide.** Green, blue, red, grey and amber are taken by the spec's semantic roles, so the accent had to be a colour none of them use.
- **Swift 5 language mode in the app target.** UIKit timer and gesture callbacks would need annotations everywhere under Swift 6 strict concurrency for no gain in a single-window app.

## Windows app (`windows/`)

- **Plain ES modules, no bundler.** The frontend runs as-is in WebView2 and in any browser, so the UI can be previewed without Rust.
- **Tokens come from Rust.** `shared/tokens.json` is compiled into the binary with `include_str!` and handed to the frontend by the `tokens` command, so there is still one definition.
- **Squircles are drawn as SVG paths**, generated with the same superellipse as `Squircle.swift` (exponent 5, 12 steps per corner, extent 1.8 × radius). CSS `border-radius` would give a different corner.
- **Text is laid out once at a reference scale** (10 px per mm) and drawn at the current zoom, so line breaks do not shift while zooming.
- **Right-click opens the same menu a hold opens.** Holding still still works; right-click is the Windows habit and changes no slot.
- **Mouse draws like the Pencil; touch follows the finger rules.** Middle-drag, Space+drag and the wheel pan, Ctrl+wheel zooms.
- **The camera is not refitted on window resize.** The iPad refits on rotation; on Windows resizes are frequent and refitting would throw away the zoom.
- **Pages are written straight to files in the repository layout.** No journal yet; that arrives with Windows sync (phase 6).

### Nav, tools and paper (Windows first, iPad to follow)

- **One nav for the whole app**, the way VADOS Gallery's `BottomBar.qml` works. Each screen hands it a kind and its buttons. When the kind changes, the old buttons pop away with `back_in` over the first `state`, the new ones pop in with `back_out` over the second, and the pill's size follows across both with `power_three_in_out`.
- **The selected tool's wash slides** like Gallery's `SectionBar.qml`. The edge in the direction of travel goes first, and the trailing edge follows `nav_trail` (60 ms) later, both over `nav_slide` with `power_two_out`.
- **Holding the nav for `nav_carry_hold` (1 s) carries it.** Touch and pen pointers are implicitly captured by the pressed button; moving the capture to the nav makes the button fire a bubbling `lostpointercapture`, which must not end the carry. It retracts into a circle under the finger and follows it. On release it turns vertical if it is nearer a side edge than the top or bottom, otherwise horizontal, and expands there. The centre is stored as a share of the window, so it keeps its place on resize.
- **Tapping the selected tool opens its second nav** beside the first, on the side that faces into the window. Pen and marker get a size slider, colour presets (as many as wanted: + saves the current colour, hold or right-click arms a preset, a second tap removes it) and a colour wheel with a hex field. The eraser gets a size slider and the two modes.
- **One pen (Kugelschreiber).** The pencil left the nav; strokes made with it still render, and its tokens stay so iPad files keep drawing the same.
- **Precise erasing replaces each touched stroke with its remaining pieces**, so files stay plain strokes. The eraser sweeps a capsule from the previous pointer sample to the current one, so a fast swipe leaves no islands. Each stroke segment is cut exactly where it leaves the capsule (radius = eraser radius plus half the stroke width, so a cut end's round cap stops at the eraser's edge). Distance to a capsule is convex along a segment, so ternary search finds the closest point and bisection finds the two boundaries. Untouched parts keep their original points. The whole drag is one undo step: tombstones for the originals and new elements for the pieces.
- **Ink is smoothed, then stored.** Raw samples are resampled every `ink.sample_spacing_points` screen points, run through a Gaussian (sigma `ink.smoothing_points`, the window shrinking symmetrically at the ends so the endpoints stay put and the tip follows the pen), and simplified with Douglas-Peucker at `ink.simplify_points`. All three are in screen points, so writing zoomed in keeps finer detail. The live stroke is the same function on the same samples, so what is drawn is what is saved. Strokes render as centripetal Catmull-Rom splines through the stored points.
- **Holding still while drawing straightens the stroke.** If the pointer stays within `ink.straighten_tolerance_points` for `stroke_straighten_hold` (1 s), the stroke eases into a straight line over `stroke_straighten_snap`; moving on drags its end until release.
- **Pen and marker keep size presets** next to the slider (`width_presets` in tokens, + saves the current size, removal as for colours). The second nav and the colour panel centre on the main nav along its axis.
- **Paper is dark by default; white is a toggle** in the top bar. Neutral inks (chroma at most `neutral_ink_chroma`) are stored as they read on white paper and are inverted on dark paper. So black pen writes white on black, the file still says black, and the iPad shows it correctly.
- **Two fingers double-tapped undo; three fingers redo.** A tap counts only if the fingers stay within 14 px and lift within 320 ms; the second tap must come within 420 ms.
- **Every Windows build on `master` is published as a GitHub release** (`windows-build-N`, marked latest), so the app is a direct download.

### Folders, notes and settings

- **Notebooks are called folders and can nest.** `parent` on `notebook.json` points at the containing folder. A parent that is missing or deleted counts as top level, so a folder never disappears. Moving refuses to put a folder inside itself or one of its descendants. Deleting a folder deletes its sub-folders and notes.
- **Notes have names, colours and icons**, as optional `title`, `color` and `icon` in the page header, written in sorted-key order only when present. NotesCore decodes, merges (newer header wins, like the rest of the header) and re-encodes them, so the iPad keeps what Windows wrote even before its UI shows them. New notes are named `Note N`.
- **Moving a note creates it again in the target folder under a new page ID and tombstones the original.** The folder is part of the file path, and rewriting a file in place under another path would look like a new page with a duplicate ID to the other device.
- **Folder and note menus share four slots in two columns**: Rename, Icon & colour, Move, Delete. Delete arms first, like every destructive slot.
- **Top bars are overlays.** The title block, back button, search field and settings button each sit on the flat 85 % panel colour, so they stay readable over ink without blur (the spec rules out blur). The canvas fits the page below the bar; pan the page under it freely.
- **One settings button on every screen** holds paper colour (dark or white) and the GitHub sync fields. The top-bar sync badge was removed; sync status lives in that sheet only.
- **The text tool opens with a blinking caret only.** No pop-in and no frame. While the box is empty a drawn accent bar blinks, the height of one line; once there is text, the native caret (accent coloured) takes over and a dashed frame marks the block.

### Ordering, search and paper bounds

- **Folders and notes carry an optional integer `order`** (in `notebook.json` and the page header, sorted-key position, omitted when absent). Siblings sort by `order`; items without one take their index among their siblings sorted by ID, so old files keep their order. New items go to the end. A reorder rewrites `order` for every sibling whose index changed, which keeps the numbers small integers instead of fractions that run out of precision. NotesCore keeps the field.
- **Drag and drop on the folder screens.** With a mouse, pressing and moving more than 8 px picks a tile up; holding still for `menu_hold` opens its menu as before. With touch and pen, a hold opens the menu, and moving on from there closes it and picks the tile up, so a plain swipe still scrolls. The tile lifts as a ghost and its place stays faded. Siblings of the same kind reorder live, with a slide. Dropping on the middle of a folder moves the item into it (a note anywhere on a folder tile), and dropping on the back button moves it one level up. The window tracks the pointer during the drag, because moving the tile in the DOM drops its pointer capture.
- **The bottom nav leaves the folder screens.** "Add folder" leads the folder grid and "Add note" leads the note grid; the nav hides with a scale-out and comes back on the page.
- **Search sits in the top bar of the folder screens** and searches every folder and note name, case-insensitively, by substring. Results show folders and notes, each captioned with its folder path. Ctrl+F focuses the field; Escape clears it.
- **Ink stays on the paper.** A stroke has to start on the paper; pressing outside pans instead. On release the stroke is clipped to the paper edge (Liang-Barsky per segment), and the pieces are saved as separate strokes in one undo step. The live stroke is clipped the same way. Text boxes start and move only inside the paper.
- **The paper has rounded corners** (`page.corner_radius`, 4 mm), and the paper is the clip for guides and ink.
- **Straightened lines snap to horizontal or vertical** when within `ink.straighten_axis_snap_degrees` (7°) of the axis.
- **Undo and redo sit under the back button** on the page, not in the nav. Undo is tinted blue (navigation), redo amber, each on a 14 % wash of its colour.
- **Text has a font size and colour in the nav while typing.** The size button shows the size in points and opens a slider plus presets (8, 12, 18, 24, 36 pt). The colour button opens fixed swatches and the colour wheel. The size is remembered and used for the next text; the colour applies to the current text only, so every new text starts in the normal text colour. Nav taps do not take focus from the text box.
- **More contrast.** The ground is darker (#0E0E0E), panels lighter (#181818), borders and secondary text brighter, and the dark paper is near black (#050505) on a lighter surround (#1C1C1C).

### Paper, text and PDF notes

- **The camera stays on the paper.** Zooming out stops at the scale that shows the whole paper below the top bar; when the paper fits along an axis it is centred, otherwise its edges cannot pass the 24 px margin. Guides and cell lines are drawn inside the rounded paper clip only.
- **Cell lines (the dashed lines between cells of an expanded note) can be turned off** from the page menu, slot 9, "Cell lines off". It is a view setting like guides, shared by all notes.
- **Tapping the folder or note name in the top bar renames it.**
- **Text is Markdown.** The file stores the raw text; the canvas renders `#`–`###` headings (1.6, 1.35, 1.15×, bold), `**bold**`, `*italic*`, `` `code` ``, `~~strike~~`, `[links](url)` (underlined), `-` bullets with two-space nesting, `1.` lists, `- [ ]` / `- [x]` tasks (done ones dimmed), `>` quotes with a bar, `---` rules and fenced code blocks. The parser lives in NotesCore (`Markdown.swift`) and `windows/src/modules/markdown.js`, with the same rules. The editor shows the raw Markdown.
- **New note asks first.** "Add note" and the page menu's "New note" open a sheet with the name (prefilled `Note N`) and Blank / PDF. Choosing PDF opens the file picker; the name follows the file name unless one was typed.
- **PDF notes follow spec 7.1.** The file is stored once as `assets/<sha256>.pdf`. The note gets one A4 cell per PDF page, stacked in rows, and one `import` element per page. An A4 page is placed `original`; any other size is `fit_cell` with a 5 mm margin, centred. Pages render with pdf.js on Windows (vendored in `windows/src/vendor/pdfjs`, version 4.10.38) and PDFKit on iPad, at a power-of-two pixels-per-millimetre level for the zoom (capped at 4096 px), cached and re-rendered when the zoom needs more.
- **On dark paper a white PDF page is shown inverted.** A page counts as white when at least 80 % of its edge samples are near white. Its colours are inverted with the hue turned 180°, so colours keep their hue, and black becomes the paper colour. Only the display changes; the asset and the export stay the original.
- **Windows reads and writes assets as raw bytes** over Tauri IPC (`write_asset` with an `asset-path` header, `read_asset` returning bytes); only `assets/<64 hex>.pdf` paths are accepted.
- **Glyph paths live in `shared/tokens.json`** (`glyphs`), as SVG path data on a 24-unit grid. Windows draws them as SVG; the iPad parses the same strings (move, line, cubic, quadratic and arc commands).
- **One release for both platforms.** `build.yml` builds the Windows app and the iPad app together and publishes `build-N` with the portable exe, both installers and `VadosNotes-iPad-unsigned.ipa`. The IPA is unsigned; it installs from Windows with Sideloadly or AltStore and a free Apple ID.
- **The iPad app now matches Windows.** Shared algorithms (smoothing, straightening, axis snap, exact cutting, paper clipping, sibling order, Markdown) moved into NotesCore with tests, so both apps compute the same strokes. Tiles on the iPad use a UIKit long press: hold opens the menu, moving on picks the tile up, a pointer right-click opens the menu.

### iPad behaviour rework (2026-10-27)

Every motion value below lives in `shared/tokens.json`; the reference is VADOS GALLERY (`core/design/.../vas/Motion.kt`, V/AS `components/16`, `18`, `19`, `24`). Where GALLERY has no equivalent, the choice is marked **Assumption**.

- **Tiles open on a tap.** The secondary-click recogniser on each tile also fired on finger taps, so a tap opened the haptic menu; it now only accepts the pointer. **Folders rename in place** by tapping their name in the top-left pill, as a note does; the haptic menu keeps Rename too.
- **The app is edge to edge.** The root ignores the safe area and hands the real insets down as `screenInsets`; the top bar, sheets, undo/redo and the nav pad themselves by them. The dark bands were the ground showing through the safe-area margins around a canvas that stopped at them. The launch colour now matches the ground (`#0E0E0E`), and the status bar is light content over the app.
- **The page fits centred.** The fit reserves the top bar's height at both ends and shows the whole note, every column and row, centred (`CanvasCamera.fitting` uses the zoom floor). It used to fit only the first cell, so a large note opened on its top left corner.
- **The camera may travel `panSlackShare` (45 %) of the screen past the paper on each axis.** Before, a fitting page was locked in the centre and a larger one could not pass the margin.
- **A finger pans; the Pencil draws.** With pen, marker and eraser, a one-finger drag pans everywhere and a finger hold still opens the page menu. Two-finger pan, pinch and the undo/redo taps are unchanged. **Assumption:** the lasso draws with the finger as well as the Pencil, since selecting is not inking and a finger-only user must still be able to select.
- **Name prompts sit at the top**, `insets.top + 24` below the edge, so the keyboard never covers them. **Settings drops in from above the top edge** (`move(edge: .top)` over `sheet_drop`, 420 ms, `back_out`) and leaves the same way in reverse (`back_in`, the time-reversed `back_out`). Sheets now close in two steps (the content leaves, then the host goes), so every sheet's leave animation plays. **Assumption:** 420 ms has no GALLERY equivalent; `overlay_enter` read as too fast.
- **Back sits directly left of settings on every screen**, in the top bar's control cluster; it pops in and out (GALLERY `TOP_ENTER` / `TOP_EXIT`) as the folder depth changes.
- **The note's created date is read from its page ID.** IDs start with ten base-32 characters of creation milliseconds, so `Identifier.creationDate(of:)` decodes them and no schema field was added. It shows as `DD/MM/YY` in 12 pt mono next to the title. **Assumption:** only the canvas top bar shows it.
- **The note name edits in place.** Tapping the title swaps the sweep title for a field in the same face, focused with the accent caret; every keystroke renames the note, and an emptied name falls back to `Note N`. **Assumption:** while editing, the name shows in the case it is typed rather than upper case.

#### Nav

- **The nav is back to its original size** (`NavMetrics.scale` 1). The 1.7× enlargement was reverted on request.
- **There are no undo and redo buttons on the page.** Undo and redo are the two- and three-finger taps and Cmd+Z / Cmd+Shift+Z.
- **Carrying the nav keeps its shape.** It no longer retracts into a circle: it lifts to `scales.held` (1.05, GALLERY `HELD_SCALE`) with an accent outline and follows the finger from the point it was grabbed. The secondary nav and colour panel pop out while it is carried and pop back in where it lands. Orientation still turns vertical near a side edge.
- **Only the two grips at the ends carry the nav**, after `navigation_grip_hold` (150 ms, GALLERY `DRAG_REST_MS`: a finger resting that long is picking something up). Holding a tool for `menu_hold` lifts it and drags it along the nav; it swaps with a neighbour once it passes half the neighbour's extent, with a segment tick, and the order is stored. The nav keeps its layout order while dragging and moves the neighbours by offsets only; on release the order is committed without animation and the lifted tool glides the remaining distance into its slot. Moving the layout during the drag made the lifted tool jump back to its old slot and spring forward. In the secondary nav the same hold lifts the whole group between dividers and reorders the groups for that tool. **Assumption:** a held colour or size preset still arms for removal as before; the group lift runs alongside it.
- **The navs avoid other UI.** The top bar's title and controls and the undo/redo cluster report their frames (`ChromeFramesKey`); the keyboard reports its height. If the nav overlaps any of them it moves to the nearest free spot found by stepping clear of each obstacle in four directions (three passes), so the keyboard pushes it straight up. The secondary nav and panel are placed beside it the same way, with the nav itself as one more obstacle. Moves use `springs.placement`. **Carrying the nav keeps its secondary nav and panel open**; they follow it without the placement spring. **The nav stays where it was picked up**: the grab offset is taken from the first drag sample. The long press reported its end before any drag sample, and the offset used to be taken from that empty sample, so the nav jumped to centre on the finger.
- **Springs.** GALLERY glides items with Compose's default `spring()` (damping 1, stiffness 1500), which is `springs.placement` (response 0.162 s, damping 1). **Assumption:** the active-tool wash uses a bouncier `springs.wash` (response 0.34 s, damping 0.55) and the secondary nav's selection ring a slightly bouncy `springs.selection` (0.3 s, 0.72); GALLERY slides its highlight on a 240 ms tween instead.
- **The press pops.** A plain button scales up to `scales.press_pop` (1.08) over `press` (80 ms, `power_two_out`) and pops back over `release` (220 ms, `back_out`). **Anything that can be held** (tiles and buttons with a hold action; not the nav, which shows no hold indicator) grows slowly to `scales.hold_grow` (1.05) over the whole `menu_hold`, linear, and at the hold threshold pops to `scales.hold_pop` (1.12) on `back_out` over `state`, together with the hold haptic (`HoldPop`). **Assumption:** 1.05 and 1.12 have no GALLERY equivalent; 1.05 matches `HELD_SCALE`.

#### Secondary nav

- **It opens like GALLERY's viewer date pill** (`TypedDatePill`), at about double its first speed: the panel pops in as a circle from its own centre (`back_out`, half of `state`) and widens from that centre to both ends (`power_three_in_out`, `state`, starting a quarter of `state` in). Every element (each preset, button, swatch and divider, not each group) pops in with its own quarter turn (`back_out`, `state`) at a random start within the first half of the 440 ms timeline (`ElementReveal`). **Closing runs it back**: the elements turn and pop out at random starts within the first 110 ms (`back_in`, `state`), the panel narrows to a circle, and the circle pops away over half of `state`. **Assumption:** "half the total time" means the start window is half of the two-`state` timeline. The scale used to run around the nav layer's corner, because the transition sat outside the positioned view; each stage is now scaled inside the panel's own frame. **Interacting with the canvas no longer closes it**; only the tool, its "…" or a new text session does.
- **Switching tools morphs it.** Groups carry stable IDs per tool, so the old ones pop out, the new ones pop in after them (GALLERY `TOP_POP_OUT` then `TOP_POP_IN`), and the panel's size follows over `state × 2` on `power_three_in_out`, as GALLERY's pill does.
- **There is no size slider in the secondary nav**; it keeps the size presets, each with its size in px under it (millimetres ÷ 0.35278, one decimal under 10), and the plus that saves the current size. **Sliding along the nav sets the selected tool's size**: a quick drag of 6 pt anywhere on the nav (well before the `menu_hold` that lifts a tool or the grip hold that carries it) sizes the selected pen, marker or eraser, or the text size while typing. The nav's items leave first (`power_two_in`, `press`), then the slider pops in from `scales.slider_enter` (0.94, `back_out`, `overlay_leave`); the nav becomes a slider of its own length with the size in px beside the knob. **Assumption:** 0.94 has no GALLERY equivalent; it keeps the pop subtle. With the text or lasso selected a drag does nothing. The drag moves the size relatively from where it was, on the same logarithmic scale as before: left to right small to big in a horizontal nav, bottom to top small to big in a vertical one. **Assumption:** the text size item slides the font size the same way.
- **Swatches and size presets sit on a 34-unit pitch** instead of 40, with no gap between them.
- **The selection ring travels.** One ring per group is a matched geometry element; picking another swatch, size or mode moves it there on `springs.selection`.
- **"…" opens a secondary nav**: Delete note, Import | Add column, Add row | Guides, Cell lines. Delete arms first (a second tap within 2.4 s deletes), like every destructive slot. Import stays disabled until importing into a note exists. Previous note, next note, new note and fit page are gone. The canvas hold menu keeps the remaining page actions as a vertical list.

#### Text and lasso

- **Finger or Pencil adds text.** A tap on the paper with the text tool starts a text box; a finger drag there still pans.
- **The text being edited has handles**, set 22 pt out from the text so they never cover it. Dragging the left or right accent handle resizes its width (at least 20 mm, kept on the paper); dragging the box moves it. Both write the session's box live (`placeText`), and finishing records one undo step that includes the box.
- **A tap on text edits it; moving it needs `text_move_hold` (600 ms).** Moving the finger before then pans (finger) or does nothing (Pencil), so taps never nudge text. **Assumption:** 600 ms, longer than `menu_hold`, because a longer hold than the menu's was asked for.
- **While text is edited, the nav shows Edit** (keyboard glyph), which brings the keyboard back if it was dismissed.
- **Lasso.** The loop is drawn dashed in the accent. On release every element the loop touches is selected (`Lasso.touches`): a stroke with any point inside or any segment crossing the loop, text or an import whose rectangle overlaps it. Requiring most of an element inside made selection unreliable. Dragging inside the selection's dashed bounds moves everything by one offset, drawn live through `RenderOptions.elementOffsets`, and commits as one undo step (`Library.moveElements`). The selection survives a tool change and clears when a finger presses the canvas outside it; a finger inside it moves it with any tool, the Pencil only with the lasso.

#### Folders and transitions

- **Groups work like GALLERY's album groups**: folders and notes can each be gathered into named groups inside a folder (`Add to group` in the item's menu; the group's own menu renames or ungroups). A group lies as a leaning stack of its cards (tilt 7°, shift 9, shrink 0.05, darken 0.2, three layers) beside its name; tapping or swiping right opens it into rows of three under a heading, swiping left or tapping the arrow folds it back. One linear clock of `stack` (360 ms), each card eased on its own, the stagger spread over `shares.stack_stagger` (0.35); opening lands on `back_out`, closing on `power_three_in_out`; the arrow travels and turns over the middle half; the shut name is cut from its left end in step. A swipe drives the same clock, decides at 0.3 and finishes only the share left. **Assumption:** groups are stored on the device (`groups.<folder>` in user defaults), as GALLERY keeps its groups in its settings rather than on disk, so no schema change was needed; grouped items are not dragged.
- **The haptic menu is a vertical list next to the finger.** Its top left corner sits 14 pt right of the touch point at the touch height; with no room on the right its top right corner sits left of it, with no room below it opens upwards, and it is clamped to the screen. It is 196 pt wide with 46 pt rows: an icon and the action, in sections split by thin dividers (Rename, Icon | Add to group, Move | Delete; Add column, Add row | Guides, Cell lines | Delete), and the destructive action always last. The panel used to be placed with an offset, so its scale-in ran from the screen corner; it is now placed by alignment guides and scales out of its own corner on `back_out` over `overlay_enter`; the rows pop in after `rise_delay` (80 ms), `rise_stagger` (40 ms) apart (GALLERY `RISE_DELAY_MS`, `RISE_STAGGER_MS`). It leaves on `back_in` over `overlay_leave`.
- **Folder to folder keeps the chrome.** Both folder routes share one screen identity, so the top bar, search, back and settings stay put and only the contents (keyed by folder) cut with GALLERY's folder transition: in from `scales.folder_enter` (0.96) after the 60 ms gate over `section_enter`, out as a 120 ms fade.
- **Opening a note flies out of its tile** (GALLERY's viewer flight, V/AS `components/16`): one progress over `viewer_enter` (280 ms, `power_two_out`), the canvas scaled from covering the tile to the screen while a rounded mask grows from the tile's frame, its corner going from 18 to 24 and gone over the last `flight_corner_fade` (30 %). The top bar, nav and undo/redo pop in once the flight is `chrome_arrival` (85 %) done, `chrome_stagger` (45 ms) apart. **Assumption:** closing a note still cuts back to the folder; shrinking back into the tile was not asked for.
- **Naming.** The new identifiers spell out "navigation"; the existing `Nav…` names (`ToolNav`, `NavItem`, `subNavKey`) were left as they are, since renaming them is a refactor nobody asked for.

#### Folder screen and canvas fixes (2026-10-27, second pass)

- **Folder tiles show their icon in the centre of the canvas area**, as the Add folder tile does, and their colour as the tile outline; the icon beside the name is gone.
- **Notes lie in a masonry grid**: columns of at least 170 pt, each note spanning as many grid columns as it has page columns and as tall as its pages, placed in the lowest free spot. A 2×1 note is twice as wide, a 1×2 twice as tall. **Assumption:** Pinterest's layout, with spans, since a note's shape is the thing to tell apart.

#### Text on the guide rows (2026-10-30)

- **The row gap is the guides' own row spacing.** `g = cell_height / round(cell_height / grid_spacing)` = 297 / 59 = 5.034 mm (`PaperGeometry.rowSpacing`, which `drawGuides` now reads too), so the rhythm keeps its phase across vertically joined cells. There is no row-gap preference (grid spacing is fixed at 5 mm), and zoom scales page millimetres as a whole. Everything below is computed from `rowSpacing` and the font, never stored, so a future preference or page type would carry through.
- **Normal text size is the size whose line is exactly one row.** `s = g / (ascender − descender + leading)`, with the metrics read from the face at 1 pt (`UIFont`, linear in size). Space Mono has 1.120 + 0.361 + 0 em, so `s` = 3.399 mm. Every line gets `minimumLineHeight = maximumLineHeight = k · g`, with `k = ceil(scale)` rows: 1 for paragraphs, lists, quotes and code, 2 for the three heading levels (×1.6, ×1.35, ×1.15) until phase 2 gives headings their own sizes. A block's height is its line count × `k · g`, replacing the old `ceil` of the measured height, which added up to 1 mm per block in page units. The `line_height` token (1.35) is no longer used by iPad text: the row is the line height. Windows still uses it.
- **Baselines sit on guide lines.** A line's target baseline is `a · s + (k − 1) · g` below its top (`a` = ascender), so a heading's baseline sits where a normal line in its last row would. TextKit's own baseline for that font and line height is measured once with an `NSLayoutManager`, and the difference is set as `baselineOffset` on every run, so the result does not depend on where TextKit puts extra space or leading. A text box's top is snapped to `round((y + a · s) / g) · g − a · s` (inside the paper), which puts the first baseline on a guide and every later one `g` below it, wrapped lines included.
- **One size, no size control.** The font-size item, its slider and its presets are gone from the typing nav, and the text tool has no secondary nav (asked and confirmed). The `font_size_range`/`font_size_presets` tokens stay for Windows.
- **Old blocks: drawn fitted, rewritten on edit** (asked and confirmed). The renderer ignores a stored `font_size` and draws at `s` from the snapped top. Opening a block to edit it, dragging it, or moving or scaling it with the lasso writes `font_size = s` and the snapped box, so Windows sees the same numbers after sync. No schema change.
- **The editor lays out like the renderer.** The text view uses TextKit 1 (`usingTextLayoutManager: false`), the same layout system as the measurement and string drawing, with the same fixed line height and offset at its zoom. After every change outside a marked (IME) range the whole storage is restyled from each character's Markdown style (phase 2), so pasted rich text cannot bring its own font or spacing.

- **The parser learned three things.** Underline tags (nested tags close innermost first; `<` is now escapable), the link's target (kept in `MarkdownStyle.linkTarget`, so an edited link is written back intact), and closing before opening: at `***` after `*a`, the open italic closes before a bold opens, where the old parser opened a bold and swallowed the rest of the line.
- **The editor shows styles, not markers** (asked and confirmed). `RichText.lines` turns Markdown into one run list per line, and `RichText.markdown` turns them back after every committed change. Inline markers are hidden and become a `MarkdownStyle` on each character (the `.markdownStyle` attribute), which the editor draws with the renderer's own run attributes. Line syntax (`# `, `- `, `1. `, `> `) stays as visible, dimmed characters, so the caret, selection and delete treat it as ordinary text and typing `# ` makes a heading. Fenced code and rules are shown and kept verbatim. Marked (IME) text is committed only when composition ends.
- **Writing Markdown back is canonical and checked.** Marks open in one order (link, underline, strike, bold, italic) and the writer closes back to the longest shared prefix, so tags always nest. Emphasis cannot start or end on a space in Markdown, so edge spaces of a bold, italic or strike span move outside its markers (underline keeps them). Text is written without escapes first. If parsing that back does not give the same runs, the line is written again with every markup character escaped, so a literal `*` never turns into emphasis and an existing note is not filled with backslashes.
- **The .md button.** While text is edited the typing nav leads with `.md`. It opens the `text-style` secondary nav through the same `toggleSubNav` switch as the colour nav. It has two groups: bold, italic, underline, strikethrough, dashed underline and inline code, then heading, bullet list and numbered list. A style shows as selected when every character of the selection has it, or when the caret's typing style has it. A line style shows as selected when the caret's line is that kind. Underline and dashed underline exclude each other.
- **Applying.** With a selection, a style is added to all of it, or removed if all of it already has it. With only a caret, the style becomes the typing style until the caret moves. Line styles act on every line the selection touches; pressing the current kind again removes its prefix, and numbered lines count from 1.
- **Headings take whole rows.** Heading scales are now 2, 1.5 and 1 (were 1.6, 1.35, 1.15), so level 1 and 2 take two rows and level 3 one bold row. The font is scaled and its baseline still lands on a guide (phase 1's offset), so the rows below keep the rhythm. Levels 4 to 6 render as level 3.
- **Known limits.** A line that only looked like a heading because its `#` was escaped becomes a heading once it is edited, because the editor shows that `#` as text. Windows still renders `<u>` tags as literal text until its Markdown module is ported.

#### Code spans and blocks (2026-10-30)

- **Stored in the same Markdown.** A code block is a fenced block with the language as its info string (```` ```javascript ````), the standard form. Inline code with a language is `` `code`{.javascript} ``, Pandoc's attribute syntax: Markdown has no other way to tag an inline span, and the code text stays literal (no HTML escaping). Plain `` `code` `` (no language) still works, and the `.md` nav's code toggle makes it. Identifiers are `javascript`, `csharp`, `java`, `python`; reading also accepts `js`, `cs`, `c#` and `py`. An unknown `{.x}` stays literal text, and `{` is now escapable, so prose that starts with `{.` after a code span is written as `\{`. No schema change.
- **The code button.** While text is edited the typing nav has a `code` item beside `.md`. It opens the `text-code` secondary nav with JS, C#, JAVA, PY and "Aa" (normal text) in one selection ring, through the same switch as the other secondary navs. The ring shows the language of the selection, the caret's code span or the caret's code block, or "Aa" when none is code.
- **What a language does.**
  - **Selection within one line:** it becomes a code span in that language.
  - **Caret only:** it becomes the typing style; inside an existing span it changes the whole span.
  - **Selection across lines:** the lines are wrapped in a fence of that language.
  - **Inside a block:** a language rewrites the block's fence.
  - **"Aa":** removes the code style from the selection or the caret's whole span. Inside a block it removes both fences, so the lines become ordinary text, and their markup characters are escaped when saved.
- **Boundaries are ordinary text.** In the editor a span is only a style on its characters, so the caret, selection and delete move across prose and code like any style change. Typing at a span's end continues the span (the character before the caret sets the typing style, as with bold).
- **On the rows.** A span is the body font at the body size with a background, so prose and code share a row. Block lines and their fences are one row each in the editor. On the canvas the fences are hidden, so the code lines move up two rows but stay on the guides.
- **Highlighting.** `SyntaxHighlighter` (NotesCore, `SyntaxHighlighter.swift`) is a small scanner per language: keywords, strings, numbers and comments. It covers line and block comments, template and triple-quoted strings across lines, escapes, and digits inside identifiers not being numbers. A block is scanned as one text, so a comment or string can span its lines. A span is scanned on its own. Plain code keeps the block's ink colour. The highlight colours and the code background are tokens per paper style (`syntax.dark`, `syntax.light`), VS Code-like hues, and the background replaces the old 14 % ink tint.

#### Library grid, drag and groups (2026-10-30)

- **Folders come first on every level.** The folder section is always above the notes, also when a folder has no notes yet. Before, a folder without notes showed its notes section (with the add tiles) above its subfolders.
- **Why the drag hunted.** The drop place was found by testing the finger against the tiles' current frames and putting the dragged tile before or after the tile under it, split at that tile's middle. Every reorder moved those frames, so the next sample hit a different tile and the order jumped again. Notes are packed into the shortest masonry column, so "before tile X" often landed far from X when the sizes differ. Release then committed whatever the last jump had produced. On pickup the ghost also played the tile entrance (faded, 14 pt low, 0.94) and grew around its centre, so the grabbed point slid off the finger.
- **The slot under the finger.** For every possible insertion index the layout of the other tiles plus the dragged one is computed with the same `MasonryLayout` the grid uses, and the index whose slot holds the finger wins; the nearest slot wins when the finger is in a gap. The current index is kept while its slot still holds the finger. This depends only on the other tiles' order, not on the live arrangement, so it cannot hunt. Release commits exactly the order on screen. The folder grid is a `MasonryLayout` of single cells now (same 230 pt minimum column and tile height), so both sections share the computation.
- **The ghost stays on the grabbed point.** It appears without the tile entrance and lifts to `scales.held` around the grabbed point.
- **Dragging into and out of groups, folders and notes alike.** Cards of an open group can be lifted like grid tiles. Dropping a tile on a group of its kind (open or shut) adds it to that group; the group shows an accent outline while it is the target. Dragging a card out of its group puts it in the grid live at the slot under the finger, and dropping there takes it out of the group at that place. Dropping a card on a folder or the back button also takes it out of its group. **Assumption:** the prompt asked for folders "the same way notes can", but nothing could be dragged into or out of a group before, so both kinds got it. Groups stay in `Preferences`, no schema change.
- **Closing an open group.** A tap on any empty space of the folder screen (the gaps of the group's own row included) and a sideways swipe that starts outside every open group close the open groups. **Assumption:** "swipe back" is read as either sideways direction, since a swipe outside a group had no meaning before.

#### Scroll bars, settings and folder colours (2026-10-30)

- **No scroll indicators anywhere.** The folder screen, settings and the move sheet hide them (`.scrollIndicators(.hidden)`), and the text editor's `UITextView` turns both off although it does not scroll.
- **Settings fill the screen.** The 820 pt cap is gone; the modules take the full width and height inside the 24 pt gutter and the top inset. They were clipped because the two columns have fixed-width parts (sliders, colour panel, swatch row) and the old `ViewThatFits` only tested the vertical axis. The columns now sit side by side when they fit across and stack when they do not. The modules always sit in a scroll view without bounce when they fit; a tap on empty space inside it closes settings, as the backdrop did.
- **The settings backdrop goes at once.** On close the black backdrop is removed without animation; the modules still pop out on their shuffled stagger.
- **Folder colours have the wheel and saved colours.** The icon and colour sheet shows the wheel button, the saved colours and a + at the end, like the toolbar colour group. The wheel opens the toolbar's `ColorPanel`; + saves the current colour; holding a saved colour arms it for removal. The saved list uses the toolbar's preset storage under its own key (`folderPresets`, starting from `folders.colors`), through the same add and remove code. The same sheet serves notes, so notes get it too.
- **Wheel drags are written once they settle.** A notebook or page colour change is a journal entry, so the colour follows the wheel on screen and is written `0.25 s` after the last move, or when the sheet closes. No schema change: the colour was already a free hex string.

#### Nav turning while carried and the folder head name (2026-10-30)

- **The nav turns while it is carried.** It used to pick its orientation only on release. Now, while carried, it takes the orientation of the edge zone it is in (nearer a side edge: vertical; nearer the top or bottom: horizontal) as soon as it crosses into another zone. A 24 pt band (`NavMetrics.turnHysteresis`) around the diagonal keeps the current orientation, so it does not flicker there.
- **The turn is a mutation.** `PillMotion.mutate` hides the elements with the nav leave pop on the new `navigation_mutate_leave` (90 ms, with the usual random spread scaled down), then turns the nav (the shell reshapes on `navigation_switch × 2`) and shows the elements again with their normal enter. Carrying continues through it: the nav keeps hit testing while carried, and the grab offset is turned with the nav so the finger stays on the same grip. A turn that is reversed before it lands just re-shows the elements.
- **The folder head name is a pill on the nav motion.** The title and count at the top left are elements on a `PillShell` driven by a `PillMotion`, like the search field. Leaving a folder plays the nav leave (elements pop out, the pill narrows and pops) instead of the old `ChromePop` scale-down, and entering plays the nav enter.
- **No head name at root.** It shows only inside a folder; going to the library or into a note plays its leave, coming back plays its enter, exactly as the search field does. It keeps the last folder's text while it leaves.

#### Tool colours, size preview, the nav over the note name and text on the rows (2026-10-30)

- **Each tool has its own colour.** The tool glyphs no longer take the ink colour; the ink colour stays on the swatch dot under the pen and marker. Pen white (`textBright`), eraser red (`destructive`), lasso yellow (`accent`), text blue (`navigation`); these reuse semantic colours of the same hue. Marker light purple, code indigo and `.md` red-pink had no matching colour, so they are new tokens under `tool_tints` (`marker #B89CFF`, `code #7A6CFF`, `markdown #FF4F8B`). The tools are always tinted, not only when selected, so they are told apart at a glance; the selection wash still marks the active one.
- **New eraser glyph.** `eraser_ring`: a stroke broken by a ring, the eraser's own cursor cutting a line. It is a new glyph key so the Windows nav, which reads `eraser`, is unchanged.
- **Text-editing nav.** `.md` and code are always tinted in their own colours. The T keeps the selected text colour and its swatch dot. The keyboard button is gone; the editor still takes focus when the block opens and on a tap into it, so its focus request plumbing was removed with it.
- **Size preview dot.** While the size slider is held for the pen, marker or eraser, a dot at the centre of the screen shows the real size on the page at the current zoom: the ink colour at the tool's opacity for pen and marker, and for the eraser the canvas eraser cursor (red ring, faint fill) at its radius. It enters and leaves with the slider's own transition and ignores touches.
- **The nav may sit over the note name.** The page title is no longer an obstacle for the nav, so the nav keeps the place it was put and no longer jumps when the title appears or changes width. The top bar sits above the screen in the view tree, so the nav, sub nav and panels report the frames they cover (`NavCoverKey`), and the page title is cut out under them (mask and hit shape, even-odd), which reads as the opaque pill lying over it. **Assumption:** cutting the title out is equal to drawing the nav on top because the pill is solid (`panelSolid`); moving the nav out of the screen's tree would have changed its layer, transitions and state.
- **The nav turns only when it touches an edge.** Moving it around no longer turns it. While carried, it turns vertical when its frame touches the left or right edge and horizontal when it touches the top or bottom (within 4 pt, `edgeTouchReach`, of the edge margin); in a corner, touching both, it keeps its orientation. This replaces the nearest-edge zones and their 24 pt hysteresis band from the previous entry.
- **Zoom while editing text.** Root cause: the editor was a sibling of the canvas in a `ZStack`, and its frame is the block's width at the current zoom. Once that was wider (or taller) than the screen, the `ZStack` grew past the screen, and the fixed frame in `TileFlight` centred the oversized stack, shifting canvas and editor by half the overflow; the page appeared to jump back. The editor is now an overlay of the canvas, which never changes the canvas's size.
- **Larger text.** The font was sized so its full line height (ascender to descender) filled one row, which left the letters at about half the row. It is now 1.2 times that (`text.row_font_scale`); line heights stay one row, so wrapping on rows and placement are unchanged. Descenders now reach a little below the block, so the editor no longer clips to its bounds. **Assumption:** 1.2 is the largest step that keeps a descender clear of the next row's capitals; the reference image did not give a number. The Windows sizes (`font_size`, its range and presets) are untouched.
- **A gap above the line.** Letters sat exactly on the ruled line. The baseline is now 0.08 mm (`text.baseline_lift`) above it in page units, so the gap grows with zoom like the line and the text, is the same for every text size, and is applied in `TextRhythm.baselineOffset`, which both the renderer and the editor use. At the zoom in the reference it is about 1.5 pt.

### Windows and Linux parity (2026-10-28)

The Tauri app was rebuilt from the iPad app, so every behaviour pass above applies to Windows and Linux too. Only the platform mappings are new.

- **Input mapping.** Pen and mouse act as the Pencil; touch acts as the finger. A pen's eraser end (`buttons & 32`) stands in for the Pencil double-tap's "switch to eraser": it erases while it touches and the tool returns on lift. Right-click opens whatever a hold opens. Wheel, Shift+wheel, Ctrl+wheel, middle-drag and Space+drag keep their earlier Windows meanings.
- **Clean taps on touch.** Two- and three-finger undo and redo count when every finger stays within 10 px and the whole touch ends within `undo_tap`, as on the iPad. Pointer events have no gesture recognisers, so the canvas tracks the touch sequence itself.
- **Springs are `linear()` easings.** Each `motion.springs` token is integrated once (stiffness `(2π / response)²`, damping `4π · fraction / response`) and sampled into a CSS `linear()` curve, so the Web Animations API plays the same spring SwiftUI does. The nav's position spring is integrated per frame instead, because it is retargeted while it moves.
- **Pops turn in CSS.** `RotatePop` is `perspective(2 × size) rotateY(-90°) scale(0.001)` with opacity, on `power_two_out` / `power_two_in`. Matched-geometry rings, washes and the variations mark are single elements that FLIP between targets on their spring.
- **The camera refits on resize,** as the iPad refits on rotation. This replaces the earlier Windows choice to keep the zoom on resize.
- **Naming sheets rise after `keyboard × 2`** unless the Virtual Keyboard API reports a touch keyboard, whose height they ride on.
- **Sync follows the iPad's protocol with a dirty-path set instead of a journal.** Local files are the merged state; `synced/` keeps the last remote bytes and `sync-state.json` the head, blob SHAs and blocked paths. Every local change marks its file path dirty with a counter. A pull merges each changed remote file into the local one with the same rules (element last-writer-wins with tombstones, header last-writer-wins, extent union), which gives the same result as replaying a journal over the new snapshot. A push sends dirty files whose bytes differ from the snapshot, then clears only paths whose counter did not move during the network calls. 409 and 422 back off and retry with `sync.backoff_seconds`. A store that has never synced counts every local file as dirty, so notes made before sync was set up are pushed.
- **The token lives in Credential Manager** (keyring crate; Secret Service on Linux, Keychain on macOS) under service `com.vaditim.notes.github`, account `token`, like the iPad Keychain item.
- **Export renders a raster PDF.** The page is drawn at up to 4 px per point (capped at 48 MP), encoded as JPEG and wrapped in a one-page PDF at the paper's size in points, then saved through a save dialog. The iPad exports vector PDF.
- **The ASCII art is compiled in from the iPad resource** (`include_str!` of `ios/VadosNotes/Resources/background.txt`), so there is one copy. The pattern is a rotated background image drifted by a Web Animation, the same tile, stagger and speed as the iPad's Core Animation drift.
- **Linux builds in the same workflow** (`linux` job: AppImage and deb) and ships in the same release.
